# 프롬프트 템플릿

AI에게 뭔가를 시킬 때 상황과 무관하게 쓸 수 있는 **일반 틀**입니다. 코드 한 줄을 고칠 때도,
분석 보고서를 쓸 때도, 문서 트리를 여러 층 만들 때도 같은 틀을 씁니다. 다층 문서 생성은
이 틀을 반복 적용하는 **특수 사례 하나**일 뿐입니다 (아래 4번 예시).

## 일반 틀 (모든 상황 공통)

```
목표 : (이 요청으로 최종적으로 원하는 게 뭔지, 한 문장)
현재 상황 : (지금 뭐가 있고 무엇이 문제/부족한지. 근거는 코드/원문 > STATUS > 설계 문서 순으로 신뢰)
범위 : (이번에 다룰 것 / 다루지 않을 것)
제약 : (건드리면 안 되는 것, 지켜야 할 규칙)
검증 기준 : (결과가 맞는지 어떻게 확인할지. AI가 인용한 줄번호/출처는 내가 직접 연다)
산출 형태 : (코드 diff / 문서 / 설명 등 원하는 출력 형태)
```

6개 빈칸입니다. 상황에 따라 일부는 한 줄로 끝나고 일부는 길어질 뿐, **빈칸 자체는 항상
이 6개**입니다.

## 왜 이 6개인가

- **목표 + 현재 상황**: "무엇을 왜"가 없으면 AI가 구조 자체를 자기 마음대로 잡습니다
  (넥슨 채용 담당자가 지적한 나쁜 예: "너가 알아서 풀어봐")
  - 현재 상황의 근거를 **문서로만** 대면, 문서가 이미 틀린 경우 그 오류가 그대로 통과합니다.
    포트폴리오 팩트체크(9/6)에서 "결론은 맞는데 근거가 틀린" 서술이 여럿 나왔고, 전부
    코드/엔진 소스를 직접 열었을 때만 걸렸습니다
- **범위**: "다루지 않을 것"을 안 적으면 AI가 요청 안 한 것까지 손댑니다
- **제약**: 기존 컨벤션/규칙과 충돌하는 결과가 나옵니다
- **검증 기준**: 결과를 받고도 뭘 봐야 맞는지 몰라서 그대로 승인하게 됩니다
  - AI가 준 인용(파일:줄)은 **그럴듯해도 틀립니다.** 같은 팩트체크에서 엔진 줄번호 셋이
    어긋나 있었습니다(368→376, 2948→2950, API 이름 하나). 인용을 받으면 열어봅니다
- **산출 형태**: 원하는 형태와 다른 걸 받아서 다시 시키게 됩니다

## 예시 1: 단일 코드 수정

```
목표 : 아이템을 컨테이너 맨 앞으로 끌 때 서버가 죽는 버그를 고친다
현재 상황 : ReorderEntry의 맨 앞 분기 조건이 컨테이너에 아이템이 2개 이상이면 항상 참이 됨
범위 : ReorderEntry 함수만. 호출부는 건드리지 않음
제약 : 기존 replication 방식 유지, UE5 reflection 매크로 규칙 그대로
검증 기준 : 아이템 2개 이상 상태에서 맨 앞으로 끌어도 서버가 안 죽는지
산출 형태 : 수정된 함수 본문 + 왜 그게 원인이었는지 한 줄 설명
```

## 예시 2: 분석/보고서형 과제 (AI 활용 역량평가 스타일)

```
목표 : 500 오류가 어떤 조건에서 발생하는지 근거와 함께 규명한다
현재 상황 : server_error.pdf에 스택트레이스, Legacy_Code_Excerpts.pdf에 관련 라우트 코드
범위 : 500 오류 원인만. 성능 저하는 다음 요청에서 따로
제약 : 제공 자료만 사용, 실행 환경 없음
검증 기준 : 근거가 된 로그 줄/코드 라인을 인용했는가
산출 형태 : 원인 + 판단 근거를 문단으로
```

## 예시 3: 이미 있는 문서의 부분 수정 (포트폴리오/지원서)

```
목표 : 2-2 해결 2를 현재 코드 기준으로 고친다 (옛 단조 클램프 서술 → 메시지 버스)
현재 상황 : EPSkillSlotWidget.cpp에 LastShownRemaining이 없음. 04_Polish_SkillDisplay.md §1이 현재 구조
범위 : 해결 2 소제목 안만. 문제 2 / 원인 2 / 다른 절은 손대지 않음
제약 : 1절과 2-1은 수정 금지. — 와 · 는 쓰지 않고 : 또는 / 로. 고치기 전에 _작업/에 백업
검증 기준 : grep -c '—\|·' 가 0. 코드 펜스 수가 짝수. 인용한 파일:줄을 내가 연다
산출 형태 : 파일 수정 + 무엇이 왜 바뀌었는지 요약. (설명만 원하면 "답변만, 파일 수정 없이")
```

**이 유형에서 특히 적을 것 둘**

- **"범위"에 "손대지 않을 절"을 이름으로.** 안 적으면 인접 절까지 같이 고쳐서 되돌리게 됩니다
- **턴 사이에 내가 파일을 직접 고쳤으면 그 사실을 적습니다.** AI가 이전 턴의 줄번호나
  문장을 기억해 치환하다가 빗나갑니다. "방금 내가 X를 고쳤으니 다시 읽고 시작해"가 한 줄이면 됩니다

## 예시 4: 다층 문서 생성 (일반 틀의 반복 적용)

머릿속에 여러 층으로 내려써야 할 구조(예: 여러 클래스가 공유할 인터페이스)가 있을 때는,
**위 일반 틀을 층마다 한 번씩, 총 세 번 채웁니다.** 새로운 틀이 아니라 아래처럼 매핑될 뿐입니다.

| 일반 틀 | 다층 상황에서의 의미 |
|---|---|
| 목표 | 이번 층에서 정할 것 |
| 현재 상황 | 이전 층에서 이미 확정된 것 (인용) |
| 범위 (다루지 않을 것) | 다음 층으로 미루는 것 |
| 제약 | 프로젝트 컨벤션 (`CLAUDE.md` 등) |
| 검증 기준 | 층 전환 게이트 (아래) |
| 산출 형태 | 문서 파일 경로/이름 |

한 프롬프트로 전체 트리를 한 번에 시키지 않습니다. 하위 층이 상위 층 확정 전에 어긋난
가정 위에서 만들어지는 걸 막기 위해서입니다.

**층 전환 게이트** (한 층 채운 뒤, 다음 층 프롬프트 쓰기 전에 확인)
```
[ ] 이 층 결과가 내 머릿속 구조와 일치하는가
[ ] Request/Answer 검토를 거쳤는가
```
둘 다 체크돼야 다음 층으로 넘어갑니다.

**층별 성격**

| 층 | 이번 층에서 다루는 것 | 절대 안 다루는 것 |
|---|---|---|
| **상위** (로드맵 문서) | 이름, 최소 시그니처, 로드맵 상 위치 | 구현체별 차이, 코드 스펙 |
| **중간** (단계 마스터 기획) | 구현체별 차이, 기존 시스템(GAS 등)과의 연결, 확장점 후보 | 실제 함수 시그니처, replication, 완료조건 |
| **리프 + STATUS** | 함수 시그니처, 클래스 계층, replication, 완료조건+함정표 | (마지막 층, 미룰 것 없음) |

### 실제 적용: 피격 인터페이스 (Player/Monster/Shield, UE5-EmploymentProj 기준)

**1번째 사용 : 상위 문서 (`DOCS.md`)**
```

현재 상황 : SSR/GAS 쪽에서 대상 타입별로 분기해서 피격을 처리하고 있음
범위 : 이번엔 이름/시그니처/위치만. 구현체별 차이, GAS 연동, 코드 스펙은 다음 층에서
제약 : DOCS.md 기존 §체계 유지
검증 기준 : 게이트 체크
산출 형태 : DOCS.md에 새 항목 한 줄 + 위치(§몇)
```
```
DOCS/DOCS.md 로드맵에 피격 인터페이스 시스템을 새 항목으로 추가합니다. 대상은 Player,
Monster, Shield 컴포넌트입니다. 지금은 타입별로 분기해서 피격을 처리하고 있어서 대상이
늘 때마다 분기가 늘어나는 게 문제입니다. 이번엔 인터페이스 이름과 최소 시그니처, 로드맵
상 위치(§몇)만 정합니다. 각 대상이 어떻게 구현할지, GAS와 어떻게 연결할지는 다음
문서에서 다룹니다.
```

**2번째 사용 : 중간 문서 (`04_Hit_DOCS.md`)**
