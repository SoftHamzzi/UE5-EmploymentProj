## 1. ★ 사실 오류 — 근거 1 "엔진이 중첩을 막는다"

인용문 두 줄은 **글자까지 원문과 일치한다.** 문제는 **적용 범위**다.

### `Class.cpp:974` — 자기 재귀만 Fatal이다

```cpp
// CoreUObject/Private/UObject/Class.cpp:966-975
FStructProperty* StructProp = CastField<FStructProperty>(ArrayProp->Inner);
if (StructProp != NULL && StructProp->Struct == this)   // ← 같은 타입일 때만
{
    //we won't support this, too complicated
    UE_LOG(LogClass, Fatal, TEXT("'Struct recursion via arrays is unsupported for properties."));
}
```

`FEPItemState` 안의 `TArray<FEPItemState>`는 Fatal이 맞다.
그러나 **다른 타입**(`FEPInventoryEntry` 안의 `TArray<FEPAttachmentEntry>`)은 이 검사에 걸리지 않는다.

### `Class.cpp:5512` — Warning이고, 금지가 아니라 강등이다

```
UE_LOG(LogClass, Warning, TEXT("Property %s contained nested NetDeltaSerialize struct '%s', ")
    TEXT("when this is not supported. Only use NetDeltaSerialize structs at class level. ")
    TEXT("Struct will replicate using non-delta serialization."));
```

경고를 뱉고 **비델타로 복제된다. 동작은 한다.**

### 결론

> `05_Loot_DOCS.md:741` "FastArray를 struct 안에 중첩하는 것도 막혀 있다 → **트리를 중첩으로 표현할 수 없다**"는 과장이다.
> 정확히는 — **동일 타입 재귀는 금지(Fatal), 이종 중첩은 델타를 잃는다(Warning).**

**결론(평면 배열 + 부모 참조)은 유지된다.** 근거가 "불가능"에서 "성능 강등 + 경고 스팸"으로 약해질 뿐이고, 근거 2(소유권·복제 증폭)와 근거 3(부착물도 아이템이다)이 훨씬 강해서 결론이 흔들리지 않는다.

**그런데 이 문장은 반드시 고쳐야 한다.** 나중에 직접 해보고 "되는데?"가 되는 순간 문서 전체의 신뢰를 잃는다. 근거의 강도 문제가 아니라 정확도 문제다.

### 부수 효과 — §4-6이 자동으로 닫힌다

혼합 탄종을 정말 원하면 탄창 `State`에 작은 배열(`TArray<FEPLoadedRound>`)을 넣으면 되고, 그건 **깊이 2가 되는 게 아니라 델타만 잃는다.** 최악의 경우에도 자료구조 깊이가 늘지 않는다.

→ **§4-6은 위험 아님. 미정에서 확정으로 옮겨도 된다.**

## 3. ★ §4-1 — 합치기. **스택이 아니다. 넣어라**

요청서의 잠정 입장("합치지 않는다")은 **돈에서 틀렸다.**

### 결정적 차이 하나 — 칸 수가 `Charges`와 무관하다

스택이 데리고 왔던 부담은 전부 **"칸 수가 개수에 비례한다"**에서 나왔다. `Charges` 합치기에는 그 성질이 없다.

| 스택이 데려오던 것 | `Charges` 합치기에서 |
|---|---|
| `SlotSize * Quantity` 계산 | **없음.** 엔트리당 고정 |
| 부분 획득 (60발 중 40발) | **없음.** 칸이 안 늘어 실패가 성립 불가 |
| `CanFit` 부분 성공 | **없음.** 항상 성공 |
| 병합 순서 규칙 (어느 스택부터 채우나) | **없음.** 대상이 하나면 하나, 여럿이면 아무거나 |
| 픽업의 수량 필드 / `bClaimed` 되돌리기 | **없음** |
| 분할 | 따라오지 않는다 (아래) |

남는 것은 획득 경로 한 곳이다.

```cpp
// AddItem 진입부. 실패할 수 없으므로 칸 검사보다 앞에 온다
if (Data->bFungible)
{
    if (FEPInventoryEntry* E = FindFungibleEntry(ItemId))
    {
        E->State.Charges += InState.Charges;
        Entries.MarkItemDirty(*E);
        return E->EntryId;
    }
}
```

### ② "스택과 실질적으로 무엇이 다른가"

`Quantity`를 되살리면 위 표의 6줄이 전부 돌아온다. `Charges` 합치기는 위 코드 3줄이 전부다. **실질적으로 더 단순하다.**

### 분할은 따라오지 않는다

분할은 자료구조 요구가 아니라 **UI 기능**이다. 안 넣으면 그만이고, 넣어도 `AddItem(ItemId, {Charges=N})` + 원본 차감 두 줄이다 — **스택의 분할과 달리 칸 수 재계산이 없기 때문**이다.

### 그리고 차감 API는 어차피 필요하다

자판기 1000원 투입(`GAME.md:64`)은 **분할이 아니라 차감**이다. `Charges -= 1000`이고, 이건 소모품 사용·재장전 탄약 소비(§8 미정 #7)와 **같은 함수**다.

```
ConsumeCharges(EntryId, N)   ← 자판기 / 소모품 / 재장전 3개를 덮는다
```

합치기를 넣으면 그 **역함수 하나**가 생기는 셈이다.

### ③ "돈만 예외"는 특수 케이스의 시작인가 — 아니다. 원칙을 세우면 속성이 된다

> **`Charges`가 균질(fungible)한 아이템만 합친다.**
> 균질 = 같은 `ItemId`면 개체 간 구별할 근거가 없다는 뜻.

| 아이템 | 균질? | 근거 |
|---|---|---|
| 현금뭉치 | ✅ | 10,000원 두 뭉치를 구별할 이유가 없다 |
| 탄약상자 | ✅ | 탄종은 `ItemId`가 이미 가른다 (`AmmoBox_545` / `_762`) |
| 무기 | ❌ | `Durability`, 부착물 자식 엔트리를 갖는다 |
| 탄창 | ❌ | 미정 #1이 `FName AmmoType`을 붙일 수 있다 |

이름은 `bMergeable`보다 **`bFungible`**을 권한다. "합쳐도 되는가"는 결과고, "구별할 근거가 없다"가 원인이다.

**그리고 이 원칙이 불변식 하나를 공짜로 준다.**

> 균질 아이템은 `Durability`를 쓰지 않는다.

합칠 때 `Durability`를 어떻게 하냐는 질문이 **아예 발생하지 않는다.** (`bMergeable`이라는 이름이었다면 발생한다.)

`FEPItemData`에 플래그 1개, 켜는 아이템 2종. `SlotSize`와 같은 급의 타입 데이터고 특수 분기가 아니다.

## 4. §4-2 `Charges` — 기준선 안 넘었다. 문제는 다른 필드다

### 전환 기준은 유효하다

`FInstancedStruct` 전환 기준은 "**전용** 필드를 요구할 때"인데, 지금은 네 카테고리가 **공유** 필드를 쓰고 있다. **방향이 반대다.**

필드가 갈라지는 게 아니라 **합쳐진** 것이고, 그건 값 타입이 맞다는 증거지 반증이 아니다. 1차 B-2 결론 그대로 유지한다.

`Charges`라는 이름도 유지 권고. "이 개체에 남은 소모 가능한 양"은 관용적 의미이고, 현금만 약간 어색한데 그건 주석 문제다 (`05_Loot_DOCS.md:104-106`에 이미 적혀 있다).

### ★ 정작 봐야 할 건 `Durability`다

```
grep -n "내구\|Durability\|수리" DOCS/GAME.md DOCS/DOCS.md
→ 0건
```

**내구도 시스템은 기획 문서 어디에도 없다.**

| 필드 | 쓰는 카테고리 |
|---|---|
| `Charges` | 4개 (무기 / 탄약상자 / 현금 / 소모품) — **살아있는 필드** |
| `Durability` | **0개** — 투기 필드 |

그리고 이건 `05_Loot_DOCS.md:800`의 자기 선언과 정면 충돌한다.

> "**필드를 지금 넣지 않는다.** 안 읽히는 필드가 방치되는 것이 `UEPItemInstance`가 5개월간 데드코드로 남은 경로 그대로다."

부착물 필드(`ParentEntryId` / `SlotId`)는 그 원칙으로 뺐는데, `Durability`는 남았다. `FEPItemData::MaxStack` "예약 필드"도 같은 문제다.

**둘 중 하나로 정리해야 한다** — GAME.md에 내구도를 추가하든가, 필드를 빼든가. 지금은 기획과 설계가 어긋난 채로 필드만 서 있다.

> `Durability`를 빼면 `FEPItemState`가 `int32` 하나가 되어 "struct가 필요하냐"가 돌아오는데, 미정 #1의 `AmmoType`이 들어올 자리라 **struct 유지는 맞다.**

## 5. §4-3 / §4-4 — 동의, 단 §4-4는 질문이 잘못됐다

### 4-3 전부 아니면 전무 — 동의

구조 문제가 아니다. 그리고 **§3의 합치기를 넣으면 완충 장치가 돈·탄약에서 그대로 복원된다** — 가방이 꽉 차도 현금뭉치와 탄약상자는 항상 들어간다(칸이 안 늘므로). 게임 필 문제의 대부분이 해소된다.

### 4-4 캐시하지 마라 — 동의

엔트리 30개 × `TMap` 조회는 **수백 나노초**다. 0.1s 틱이면 초당 300회 — 측정 자체가 안 되는 수준이고, 캐시가 만드는 3경로 동기화 버그가 압도적으로 비싸다.

**다만 답이 "캐시하지 마라"가 아니라 "폴링하지 마라"여야 한다.**

프롬프트가 용량을 표시한다면 FastArray의 `PostReplicatedAdd` / `PostReplicatedRemove` / `PostReplicatedChange`에서 델리게이트를 쏘면 **0.1s 폴링 자체가 사라진다.** Step 04가 이미 이 방식이면 4-4는 질문이 성립하지 않는다.

### ★ 진짜 위험은 성능이 아니라 null이다

```cpp
UsedSlots += FindData(E.ItemId)->SlotSize;   // ← nullptr이면?
```

DT에 없는 `ItemId`가 들어오면 그 아이템은 **칸을 0으로 먹는다.** 결과는 "가방이 무한대"고, **무증상이다.** `ensure` + 경고 로그가 필요하다.

## 6. §4-5 부착물 파급 — 문서가 요청서보다 앞서 있다

`05_Loot_DOCS.md:789-800`의 비용표가 이미 6개를 열거하고 있고, `GetUsedSlots()`의 부모 필터(`:794`)와 `AEPWeapon` 메시 부착(`:798`)까지 들어 있다.

> **"`AEPPickup`만 모양이 바뀐다"는 단정은 문서 안에서 이미 반박돼 있다.** 요청서 §4-5의 서술이 문서보다 뒤처졌다.

그 비용표에도 **없는 것 3개:**

### ① `RemoveEntry()`의 자식 캐스케이드 — 제일 중요하다

무기 엔트리를 지울 때 자식 3개를 같이 지우지 않으면 **고아 엔트리**가 남는다. 칸은 안 먹지만(부모 필터) UI에 안 보이고 영원히 살아 있으며, **세이브에 그대로 실린다.**

**값 타입 설계에서 유일하게 살아남는 "고아" 개념**이고, 하필 §4-1이 UObject를 버린 이유가 고아 누수였다. 깊이 1이라 한 줄이지만, 그 한 줄이 반드시 있어야 한다.

### ② `EquippedEntryId`의 write-back 대상이 자식이 될 수 있다

미정 #1을 ⓐ(탄창 = `[Mag]` 부착물)로 정하면 잔탄 write-back 대상이 **무기 엔트리가 아니라 자식 엔트리**다. §4-7 순서 규칙이 자식까지 커버해야 한다.

### ③ 스탯 합산 주입 지점 — 비용표는 "`UEPCombatComponent`에 주입"이라고만 적었다

현재 `Recoil` / `Spread` / `MaxAmmo`는 GAS 어트리뷰트가 아니라 **`WeaponDef->` 직접 읽기**다. 그래서 GE로 줄 수가 없다.

최소 변경은 **합산 결과를 `AEPWeapon`에 캐시하고, `UEPCombatComponent`가 `WeaponDef->` 대신 그 캐시를 읽게 하는 것**이다. 읽는 지점을 한 곳으로 모으는 것이 **부착물 전 단계에서 미리 해둘 수 있는 유일한 준비**다.

### 반대로 안심해도 되는 것 — `AddItem`의 원자성

부착물 달린 무기 획득 = 엔트리 4개 삽입이지만, **칸은 부모만 먹으므로 부모가 들어가면 자식은 반드시 들어간다.** 부분 실패가 성립하지 않는다. 롤백 로직이 필요 없다.

루트테이블 사전 부착과 프롬프트 표시를 지금 넣지 않는 판단에는 동의한다.

## 7. §5-2 설계 반론 4건

### ① `AddItem` → `int32 EntryId`: 좋다. 단 함정이 하나 생겼다

`bool` + out 파라미터보다 낫고 UE 관례(`TArray::Add`가 인덱스 반환)와도 맞다. 그런데 **`INDEX_NONE`은 `-1`이라 truthy다.**

```cpp
if (Inventory->AddItem(ItemId, State))   // ← 실패(-1)를 성공으로 읽는다
```

`bool` 반환이었으면 불가능했던 오독이다. `EntryId`가 1부터 시작해 0이 안 나오는 것도 여기서는 도움이 안 된다.

→ **`!= INDEX_NONE` 강제를 Step 03 함정표에 넣어라.**

### ② 목록 + 칸 게이지: 후퇴 아니다

칸 합산은 배그 모델이고, 배그 UI는 목록 + 무게 게이지다. 격자를 흉내내면 **"5칸짜리 무기를 어느 칸에 그리나"라는, 원래 없던 배치 문제를 UI에서만 되살리게 된다.**

덤으로 **결정 B와 일관된다** — 부착물 트리 표시가 목록에서는 들여쓰기 한 줄인데, 격자에서는 별도 화면(배그의 무기 상세창)이 필요하다.

### ③ `UListView`를 지금 안 넣는 것: 맞다. **그런데 이유가 성능이 아니다**

```cpp
// UMG/Public/Components/ListView.h:38
class UListView : public UListViewBase, public ITypedUMGListView<UObject*>
```

**`UListView`의 아이템 타입은 `UObject*`로 고정돼 있다.** 도입하면 엔트리마다 UObject 래퍼를 만들어 `SetListItems`에 넘겨야 한다 — **방금 지운 `UEPItemInstance`를 UI 전용으로 부활시키는 것**이고, 수명 관리까지 딸려온다.

즉 "지금은 30행이라 괜찮다"가 아니라 **"값 타입 설계에서는 수동 재생성이 오히려 정합적"**이다. 나중에도 `UListView`로 가는 게 아니라 **풀링을 직접 넣는 쪽**이 맞다.

### ④ write-back 순서 중복 서술 — 문서로 풀지 말고 코드로 없애라

두 문서에 규칙을 적어두면 **한쪽만 고쳐지는 사고는 반드시 난다.** 참조로 바꾸는 건 반쪽 해법이고, 최선은 **순서 규칙을 함수의 내부 불변식으로 밀어넣는 것**이다.

```cpp
void UEPInventoryComponent::RemoveEntry(int32 EntryId)
{
    if (EntryId == EquippedEntryId) WriteBackEquippedState();   // 내부에서 보장
    // ... 제거
}
```

이러면 "호출 순서를 지켜라"라는 규칙 **자체가 사라지고**, 두 문서 모두 "`RemoveEntry()`가 보장한다" 한 줄이 된다.

**`MarkItemDirty` 누락도 같은 방식으로 없앨 수 있다** — 원시 엔트리 접근을 막고 `SetEntryCharges(EntryId, N)`만 노출하면 호출자가 잊을 방법이 없어진다.

### ★ 이것이 §4 전체를 관통하는 유일한 실무 지적이다

> 지금 남은 위험은 성능도 확장성도 아니고, **코드로 강제 가능한 불변식을 문서 규칙으로 남겨둔 것들**이다.
> (write-back 순서 / `MarkItemDirty` / `INDEX_NONE` 검사)
> 1인 프로젝트에서도 3개월 뒤에는 깨진다.
