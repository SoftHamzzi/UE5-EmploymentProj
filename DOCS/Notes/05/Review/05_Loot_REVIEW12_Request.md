## 0. 사용자 입장 (먼저 밝힌다)

**11차 답변은 전부 수용해 반영했다.** 답변이 잡은 결함 둘(`SortKey` 동률 / 재정규화가 이분 고갈에만) 다 코드로 재현했고, `Server_ReorderEntry` RPC를 04-B로 옮긴 것도 `Owner`를 `TObjectPtr<UActorComponent>`로 바꾼 것도 반영했다. 답변과 다르게 판정한 셋은 `LOOT_STATUS.md`와 `EquipmentSlots.md` §13-7에 적었다.

**그런데 반영 후 스스로 검증하다 하나를 더 찾았다.**

11차 답변 §3-3은 *"키 공간은 `GetSortedContents`가 아니다"* 를 처방하면서 고칠 곳을 **넷**으로 지목했다 — `NextKeyAtEndOf` · `InsertEntry`의 삼항 · `MoveEntry`의 `:720` 예외 · `RenormalizeSortKeys`. **`ReorderEntry` 자신이 빠졌다.** 그 함수도 같은 방식으로 틀렸다(§1).

**고치는 방법은 명확한데, 고치고 나니 판정이 필요한 것이 하나 나왔다(§2).** 그게 이번 요청의 본론이다.

**이번에 볼 것은 셋뿐이다.**

1. **§1 — `ReorderEntry`의 틈 계산.** 결함이 맞는지, 처방이 맞는지
2. **★ §2 — 슬롯에 들어간 아이템이 "자리를 지키는가".** 11차 검수가 만든 부수 효과인데 **의미론 판정이 안 된 채로 들어갔다**
3. **§3 — 11차 답변과 다르게 판정한 셋이 맞는지**

## 1. `ReorderEntry`가 틈을 "보이는 목록"에서 구한다

### 1-1. 재현

```
본체:  붕대 0        AK 65536 (Hotbar1 슬롯)        구급상자 131072
       GetSortedContents(-1) = [붕대, 구급상자]        ← AK는 걸러진다

"붕대 뒤"에 X를 놓는다  →  ReorderEntry(X, 붕대)
    PrevKey = 0
    다음 = Sorted[1] = 구급상자 = 131072
    NewKey = 0 + (131072 - 0) / 2 = 65536              ← ★ AK와 동률
```

**11차 답변이 잡은 함정 4q와 같은 뿌리다** — *"키 공간을 표시 목록으로 계산했다."* 답변은 발급 경로(`InsertEntry` → `NextKeyAtEndOf`)와 재정규화만 고쳤고, **재배치 경로는 그대로였다.**

**세 분기 전부 해당한다.**

| 분기 | 초안 식 | 겹칠 수 있는 대상 |
|---|---|---|
| 맨 앞 | `KeyOf(Sorted[0]) - Step` | `Sorted[0]`보다 **아래에 있는 슬롯 형제** |
| 맨 뒤 | `PrevKey + Step` | Prev보다 **위에 있는 슬롯 형제** |
| 사이 | `PrevKey + (KeyOf(Sorted[Idx]) - PrevKey) / 2` | 두 이웃 **사이에 낀 슬롯 형제** |

### 1-2. 도달 가능성

**위 예가 그대로 정상 플레이다.** 본체에 아이템 셋, 하나를 핫바에 꽂은 상태에서 나머지 순서를 바꾼다. 11차 답변이 *"가장 흔한 조작 순서"* 라고 부른 것과 같은 상황이고, **키 간격이 `Step`의 배수로 정렬돼 있을 때 중점이 정확히 슬롯 형제의 키가 된다** — 재정규화 직후가 정확히 그 상태다.

### 1-3. 처방 — `Prev`는 보이는 목록, **틈은 부모 전체**

```cpp
const int32 PrevKey = (PrevEntryId == INDEX_NONE)
    ? MinKeyUnder(Container) - SortKeyStep                   // 부모 전체의 최소보다 한 칸 앞
    : KeyOf(PrevEntryId);

const int32 NextKey = NextKeyAbove(Container, PrevKey, /*Exclude=*/EntryId);   // 없으면 INDEX_NONE
const bool  bTail   = (NextKey == INDEX_NONE);

int32 NewKey;
if (PrevEntryId == INDEX_NONE) NewKey = PrevKey;
else if (bTail)                NewKey = PrevKey + SortKeyStep;
else                           NewKey = PrevKey + (NextKey - PrevKey) / 2;
```

**`Prev` 유효성 검사는 그대로 둔다** — *"같은 컨테이너의 **수납** 형제인가"*(슬롯이면 거부). 사용자가 볼 수 없는 것을 기준으로 삼을 수는 없기 때문이다.

**즉 규칙이 이렇게 갈린다.**

| | 어디서 오나 |
|---|---|
| **`Prev` (사용자 의도)** | **보이는 목록** — `GetSortedContents` |
| **틈 (키 공간)** | **부모 전체** — 슬롯 포함 |

헬퍼 둘이 는다: `MinKeyUnder(Container)` · `NextKeyAbove(Container, Key, Exclude)`.

### 1-4. 판정 요청

- **결함이 맞는가.** 특히 *"재정규화 직후에 중점이 정확히 슬롯 형제의 키가 된다"* 가 맞는지
- **처방이 맞는가.** `Prev`는 표시 목록 / 틈은 부모 전체라는 이 비대칭이 옳은가, 아니면 양쪽 다 한쪽으로 통일해야 하는가
- **헬퍼 둘을 늘리는 것이 맞는가.** `NextKeyAtEndOf`와 합쳐 하나로 만들 형태가 있는가 (셋 다 "부모 전체를 훑어 경계 키를 구한다"이다)

## 2. ★ 슬롯에 들어간 아이템이 "자리를 지키는가" — 의미론 판정

### 2-1. 이게 어떻게 생겼나

11차 답변 §3-3이 예외 셋을 없애라고 했고(`InsertEntry` 삼항 · `MoveEntry`의 `NewSlotId` 조건 · `RenormalizeSortKeys` 필터), 그 결과 **슬롯에 든 아이템도 키를 계속 들고 있게** 됐다. 답변은 이걸 **이득**으로 적었다.

> *"부수 효과가 좋다 — 무기를 뺐다 꽂으면 원래 자리로 돌아온다. 키를 계속 들고 있었기 때문이다. 지금 설계에서는 맨 뒤로 간다."*

**동의해서 반영했다. 그런데 §1을 고치다 보니 그 선택에 뒷면이 있다.**

### 2-2. 뒷면

```
본체:  붕대 0     AK 65536 (Hotbar1 슬롯)     구급상자 131072
       화면에는 [붕대, 구급상자] 두 칸만 보인다

사용자가 X를 "붕대 뒤"(= 화면 두 번째)에 놓는다   →  X = 32768
       화면: [붕대, X, 구급상자]                      ← 의도대로다

AK를 해제한다                                     →  AK = 65536 그대로
       화면: [붕대, X, AK, 구급상자]

...인데 X를 "두 번째"에 놓았을 때 AK가 세 번째로 돌아온 것은 우연이다.
X를 "구급상자 앞"(= 화면 두 번째, 같은 자리)에 놓으면 X = 98304 이고
       화면: [붕대, AK, X, 구급상자]                  ← 같은 화면 자리에 놓았는데 결과가 다르다
```

**같은 화면 위치에 놓아도 보이지 않는 이웃이 어느 쪽이냐에 따라 해제 후 순서가 갈린다.** 사용자는 AK가 거기 있는 줄 모른다.

### 2-3. 두 안

| | **A. 자리를 지킨다** (현재, 11차 답변 권고) | **B. 자리를 포기한다** |
|---|---|---|
| 슬롯에 넣을 때 | 키를 **그대로 둔다** | 키를 **부모 맨 뒤로 민다** |
| 뺐을 때 | **원래 자리로 돌아온다** | **맨 뒤에 붙는다** |
| 보이지 않는 이웃 | **있다** — §2-2의 갈림 | **없다.** 슬롯 아이템은 항상 표시 목록 밖·위 |
| §1의 틈 계산 | 부모 전체를 봐야 한다 | **표시 목록만 봐도 된다** (슬롯 키가 전부 뒤에 있으므로) |
| 함정 4q | 스코프 교정으로 막는다 | **구조적으로 안 난다** |

**B가 더 단순하다.** §1의 결함이 통째로 사라지고 헬퍼 둘도 필요 없다.
**A가 더 친절하다.** 무기를 잠깐 꽂았다 빼는 것이 배치를 안 흔든다.

### 2-4. 내 판단이 갈린다 — 그래서 묻는다

- **A를 지지하는 것:** 핫바 1~4는 **자주 꽂았다 뺀다.** 그때마다 가방 배치가 흔들리면 정리한 보람이 없다
- **B를 지지하는 것:** §2-2의 갈림은 **설명할 수 없는 동작**이다. 그리고 A는 §1·4q·4s를 전부 만들어낸 원인이기도 하다

**그리고 A/B 말고 C가 있는지도 봐달라** — 예: 슬롯에 들어갈 때 키를 유지하되 **표시 목록 기준으로 재배치를 해석**해 §2-2를 없애는 형태.

### 2-5. 판정 요청

- **A / B / C 중 무엇인가**
- **B라면** 11차 답변 §3-3의 *"부수 효과가 좋다"* 가 뒤집힌다 — 그게 맞는가
- **A라면** §2-2의 갈림을 UI로 가릴 수 있는가 (예: 슬롯 아이템도 구획에 흐리게 표시)

> **참고: 핫바 5~0(참조 방식)은 이 문제가 없다.** `SlotId`를 안 쓰고 아이템이 컨테이너에 그대로 남기 때문이다(`EquipmentSlots.md` §5). 즉 이 판정은 **핫바 1~4와 착용 8슬롯**에만 걸린다.

### 4-1. ★ 반영 중 내가 만든 stale 둘도 고쳤다 (배경)

11차 답변을 적용하면서 **내가 직접 만든 모순 둘**이 있었고 발견해 고쳤다. 검수 대상은 아니지만 적어둔다.

1. **`SortKey` 필드 주석**이 *"`SlotId`가 있으면 무의미하다"* 로 남아 있었다 — 스코프 교정으로 **슬롯 아이템도 키를 갖게 됐으므로 거짓**이 됐다
2. **함정 4p**가 *"`InsertEntry`가 슬롯이면 0, `MoveEntry`가 `NewSlotId.IsNone()`일 때 재발급"* 이라고 **방금 없앤 규칙을 처방**하고 있었다

**둘 다 "고친 코드와 그것을 설명하는 문장이 따로 논다"는 같은 종류다.** 11차 답변이 `:820`(*"겹칠 문법이 없다"*)에 대해 지적한 것과 정확히 같은 자리다.
