## 1. 목표

아이템이 **서버 권한으로 보관되고, 소유 클라이언트에만 델타 복제된다.** 칸 합산·슬롯 정합·표시 순서까지가 이 구간이다. 줍기·버리기는 없다 — 아이템은 치트 커맨드로 만든다.

**2026-10-07부터 셋이 더 붙는다.** 아이템마다 **바뀌지 않는 정체**가 있고, 조회가 **엔트리 수가 수천이어도** 겹쳐 느려지지 않으며, **누구에게 복제할지를 컴포넌트가 정한다**(상자·시체가 같은 컴포넌트를 쓰는 날 코드를 고치지 않게).

## 3. 불변식 — 코드가 이걸 지키는지 보며 읽고, 고친 뒤에도 지키는지 본다

**식별**
1. 엔트리는 `EntryId`로만 가리킨다. 배열 인덱스로 가리키지 않는다.
2. `EntryId`는 한 번 발급되면 다시 쓰이지 않는다(넣고 빼도 기존 번호가 밀리거나 재사용되지 않는다).

**쓰기**

3. 엔트리를 바꾸는 곳은 정해진 몇 함수뿐이고, 바꾼 곳에서 반드시 복제 표시(dirty)를 남긴다.
4. 쓰기는 서버만 한다. 클라에서 불려도 상태는 안 바뀐다.
5. 살아 있는 엔트리를 통째로 대입하지 않는다(필드 단위로 고친다).

**칸**

6. 한 컨테이너의 사용 칸 = 그 컨테이너에 **수납된**(슬롯이 아닌) 아이템의 `SlotSize` 합. 개수가 아니다.
7. 컨테이너마다 칸은 독립이다. 본체·상의·배낭이 합산되지 않는다.
8. 균질 아이템(`bFungible`) 합치기는 **같은 컨테이너 안에서만** 일어난다. **균질 아이템은 `Stats`가 비어 있다** — 합칠 때 버려질 수치가 없어야 합치기가 성립한다. 비어 있지 않은 것은 들어오지 못한다 (2026-10-08, D-108).
9. 넣을 수 없으면 아무것도 바뀌지 않는다.

**슬롯**

10. 슬롯에 든 것은 칸을 먹지 않는다.
11. 몸 슬롯은 본체(부모 없음)에만 있다. 한 슬롯에는 하나만.
12. 어떤 엔트리도 자기 자신이나 자기 후손 안으로 들어가지 않는다.
13. 제자리로 옮기면 아무것도 바뀌지 않는다.

**표시 순서 (`SortKey`)**

14. 화면 순서는 서버가 정하고, 클라와 서버가 같은 순서를 그린다.
15. 새 키를 정할 때 보는 범위(키 공간)는 **같은 부모의 형제 전부**다. 화면에 보이는 목록과 다를 수 있다.
16. 키는 배열 상태를 바꾸기 **전에** 구한다.
17. 다른 컨테이너로 옮긴 엔트리는 목적지의 맨 뒤에 놓인다.
18. 키는 음수도 0도 정상 값이다. 그래서 "못 찾았다"를 키 값으로 표현하지 않는다.
19. 틈이 바닥나거나 경계에 가까워지면 순서를 유지한 채 다시 깐다. 어떤 입력에서도 끝난다(무한 재귀 없음).
20. 원래 자리에 도로 놓으면 키가 바뀌지 않는다. **틈이 이미 바닥난 상태여도 마찬가지다** — 다시 까는 일도 일어나지 않는다.

**복제·알림**

21. 인벤토리는 소유 클라에게만 복제된다. **누구에게 갈지는 프로퍼티가 아니라 컴포넌트가 정한다.**
22. 변경 한 묶음(또는 수신 한 번)마다 알림은 **한 번** 나간다.

**정체 (2026-10-07, D-098)**

23. 아이템의 정체는 세상에 **처음 생길 때 한 번** 정해지고, 어느 컨테이너로 옮겨도 · 버렸다 주워도 같다. 바뀌는 것은 `EntryId`뿐이다. **블루프린트도 정체를 쓸 수 없다.**
24. 한 컴포넌트 안에 같은 정체가 둘 있을 수 없다. **정체가 없는 상태는 인벤토리에 들어오지 못한다.** 거절되면 번호도 소모되지 않는다. **합쳐지는 경우도 마찬가지다** — 합치기도 "들어오는 것"이다 (2026-10-08, D-104).
25. 균질 아이템을 합치면 **받는 쪽의 정체가 남는다.**
26. 정체는 클라이언트에 가지 않는다.

**종류별 수치 (2026-10-07, D-099)**

27. 종류별 수치는 **태그가 이름**이다. 종류가 늘어도 구조체 모양이 바뀌지 않는다.
28. 수치를 쓰는 곳은 하나다(가드 · dirty가 거기 있다). **블루프린트도 예외가 아니다.**

**파생 색인 (2026-10-07, D-100)**

29. 엔트리 배열을 처음부터 끝까지 도는 곳은 **한 곳**이다. 다른 조회는 전부 색인을 지난다.
30. 색인은 진실이 아니다 — 언제 버려도 다시 만들어 **같은 답**을 낸다. 복제도 세이브도 하지 않는다.
31. 색인이 담는 것(위치 · 부모 · 슬롯 · 정체 · 칸)을 바꾸는 쓰기나 클라 수신이 일어나면, **그다음 조회는 반드시 새 상태를 본다.** 색인이 담지 않는 것(키 · `Charges` · 수치)을 바꾸는 쓰기는 색인을 건드리지 않는다.
32. 쓰기는 **배열 원소 자체**에 한다. 복사본에 쓰고 `true`를 돌려주는 일이 문법적으로 없다.
33. 구조를 바꾸는 호출을 지나서까지 원소를 가리키는 것(포인터 · 참조 · 색인 안 목록의 참조)을 들고 있지 않는다.

**가시성 (2026-10-07, D-101)**

34. 설정 하나가 빠졌을 때 인벤토리는 **새지 않고 끊긴다** — 남에게 보이는 쪽으로 실패하지 않는다.
35. 컴포넌트가 사라지면 가시성 등록도 같이 사라진다.

**일괄 경로 (2026-10-08, D-106)**

36. 여러 엔트리를 한 번에 넣거나 빼는 조작에서 **색인을 다시 만드는 횟수는 엔트리 수에 비례하지 않는다.** 읽기 · 바꾸기 · 읽기가 엔트리마다 번갈아 나오면 이 불변식이 깨진다.

**리스트와 컴포넌트의 경계 (2026-10-11, D-113 · D-114)**

37. 원소를 더하거나 빼는 함수는 **복제 표시와 색인 무효화를 같은 함수 안에서** 한다. 둘 중 하나만 하는 경로가 없다.
38. 리스트는 권한 · 알림 · 게임 규칙을 모른다. 그래서 리스트의 구조 변경은 **알림 가드를 든 컴포넌트 함수 안에서만** 불린다.
39. 컴포넌트에는 색인도 발급 상태도 없다. const 조회가 상태를 고치는 일(`mutable`)은 리스트 안에서만 일어난다.

## 5. PIE 검증

**설정:** Net Mode `Play As Client`, 플레이어 2. 커맨드는 각 클라 창 콘솔에서 친다. `EPInvAdd`·`EPInvMove`·`EPInvReorder`·**`EPInvDumpServer`** 는 서버로 라우팅되고(친 사람의 인벤토리. **`DumpServer`의 출력은 서버 쪽 로그**에 찍힌다), `EPInvDump`·`EPInvDumpAll`은 로컬(그 창의 복제본)에서 돈다.

> **준비 — 데이터 둘이 채워져 있어야 슬롯 이동(7 후반·17)이 된다.** ① Project Settings의 Loot 설정 `BodySlots`(몸 슬롯 12: `Hotbar1`~`4` + 착용 8, 이름은 `DOCS/Mine/EquipmentSlots.md`) ② `DT_Items` 배낭·무기 행의 `SlotPriority`(`["Back"]`, `["Hotbar1", …]`). **2026-10-04 확인 시 `BodySlots`는 C++ 기본값도 `DefaultGame.ini` 항목도 없어 빈 배열이었다** — 이 상태면 슬롯 이동은 전부 거절된다.
>
> 아이템 이름(`Bandage`, `Cash_10000`, 배낭·무기 행)은 `DT_Items`에서 확인한다. 아래 표의 행 이름은 예시다.
