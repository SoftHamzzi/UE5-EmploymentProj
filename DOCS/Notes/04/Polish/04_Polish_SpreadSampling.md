# Polish — 탄퍼짐 CDF 샘플링 방식 검토

**상태:** 설계 검토만 완료, 미구현. 지금 코드(`AEPWeapon::SampleSpread`, X축 균등 + 이진탐색)는
그대로 두고 있다 — 256칸에서 최악 8회 비교로, 현재 규모(펠릿 수 자릿수)에서 바꿀 이유가 없다.
여기 적어두는 건 다음에 "왜 안 바꿨는지"와 "바꾼다면 뭘로" 둘 다 다시 유도하지 않기 위해서다.

관련 소스: `EPWeapon.h/.cpp`(`SpreadCDFTable`, `BuildSpreadCDFTable`, `SampleSpread`).
원 설계는 `04_GAS_05A_Spread.md` 참고 — 거기는 "무엇을 만들었나", 여기는 "그 구조를 최적화하면
어디로 가는가"다.

---

## 1. 지금 구조

X축(반경비율 0~1)을 256등분해서 각 칸의 누적확률(CDF)을 구워둔다(`BuildSpreadCDFTable`,
`BeginPlay` 1회). 샘플링(`SampleSpread`, 매 펠릿)은 균등 난수 `U`를 그 CDF 배열에서
이진탐색으로 찾아 역변환한다.

```cpp
int32 Lo = 0, Hi = CDFTableSize - 1;
while (Lo < Hi)
{
    const int32 Mid = (Lo + Hi) / 2;
    if (SpreadCDFTable[Mid] < U) Lo = Mid + 1;
    else Hi = Mid;
}
return static_cast<float>(Lo) / CDFTableSize;
```

**현재 정확도 문제:** 칸을 찾은 뒤 보간 없이 `Lo / CDFTableSize` 하나로 스냅한다. 칸의 해상도
자체(1/256)는 PDF와 무관하게 균일하지만, 같은 칸에 떨어진 샘플은 전부 같은 값을 받는다.
PDF가 높은 구간(중심 집중 커브의 정점 등)일수록 그 칸에 떨어지는 샘플 수가 많아서, 계단식으로
겹치는 탄착 아티팩트가 그 구간에서 더 눈에 띌 수 있다 — 칸 안에서 선형보간을 추가하면 없앨 수
있다 (아래 2번의 전제이기도 하다).

---

## 2. 검토한 대안: Y축(확률) 균등 + 퀀타일 테이블

X축 대신 Y축(0~1 확률)을 256등분해서, 각 확률 지점에 대응하는 반경 X를 **미리 뒤집어(역함수,
quantile function) 저장**해두는 방식.

```cpp
// 빌드 시(무기당 1회): 원본 CDF(RawCDF, X 256개)를 Y 균등 격자로 재보간
// QuantileTable[i] = CDF^-1(i / 256), 선형보간으로 계산

// 샘플링 시(매 펠릿): 탐색 없이 직접 인덱싱
const float Pos = U * CDFTableSize;
const int32 Idx = FMath::FloorToInt(Pos);
const float Frac = Pos - Idx;
return FMath::Lerp(QuantileTable[Idx], QuantileTable[Idx + 1], Frac);   // O(1)
```

### 정확도: 보간을 더하면 두 방식이 동등하다

처음엔 "Y를 균등 분할하면 PDF가 낮은(완만한) 구간에서 `dX/dY`가 커져 X 오차가 커진다"고
판단했다. **이건 퀀타일 테이블을 보간 없이 만들 때만 맞는 말이다.** 빌드 시점에 원본 CDF
샘플 사이를 선형보간해서 퀀타일 테이블을 채우고, 런타임에도 인접 칸 사이를 보간하면 원본
CDF를 그대로 재구성하는 것과 수학적으로 같아진다 — 정확도 차이가 사라진다.

### 남는 차이는 "탐색을 없애는 것"뿐이다

보간 자체는 두 방식 다 **매 샘플마다** 필요하다(칸을 찾은 뒤 그 안에서 보간하는 마지막 한
스텝은 피할 수 없다). Y축 균등 방식이 아끼는 건 그 앞 단계, **"어느 칸인지 찾는 탐색"**이다.

| | 칸을 찾는 비용 | 칸 안에서 보간하는 비용 | 빌드 비용 |
|---|---|---|---|
| X 균등(지금 코드) | 이진탐색 O(log 256) | O(1) | O(256) — PDF 256점 평가 |
| Y 균등(퀀타일 테이블) | 인덱싱 O(1) | O(1) | O(256) — 두 CDF를 투 포인터로 병합 |

빌드 비용은 둘 다 무기당 1회, 같은 자릿수(O(256))다. 이진탐색을 인덱싱으로 바꾸는 대신
빌드 로직이 "PDF를 256점 적분"에서 "CDF를 Y 격자로 재보간(투 포인터 병합)"으로 조금
복잡해진다.

### 결론

**보간을 넣는다는 전제에서는 Y축 균등(퀀타일 테이블) 쪽이 현재 알려진 방식 중 가장 효율적이다.**
런타임 비용이 이진탐색(비교 8회)에서 인덱싱(곱셈+뺄셈 1회)으로 줄고, 정확도 손실은 없다.
다만 샷건 한 발에 펠릿 몇 개 규모에서는 8회 비교조차 체감되지 않아서, **지금 코드를 바꿀
실익은 없다.** 펠릿 수가 크게 늘거나(수백 발 단위) 이 함수가 실제 핫패스가 되면 그때
퀀타일 테이블 + 빌드 시 투 포인터 병합으로 옮기는 걸 고려한다.

## 3. 참고: 앨리어스 메서드 (다른 문제에 쓰는 도구)

**Walker's Alias Method** — 이산적인 항목을 가중치에 비례해 O(1)로 뽑는 표준 기법.
확률(prob)과 대체 인덱스(alias) 두 배열을 같이 저장해서, 균등 난수 하나로 항목과 그 항목을
받아들일지/이웃 것을 받을지를 한 번에 결정한다. 빌드는 O(N)(큐 두 개로 균형 맞추기), 샘플링은
항상 O(1)이고 근사가 아니라 **정확**하다.

**여기 탄퍼짐엔 안 맞는다.** 앨리어스 메서드는 "N개의 이산 항목 중 하나를 가중치대로 고른다"는
문제용이다. 탄퍼짐은 반경이라는 **연속값**을 커브(PDF)에서 뽑는 문제라 이산 항목이 없다 —
256칸으로 이산화한 것 자체가 연속 분포를 근사하기 위한 수단이지, 그 칸들이 서로 다른 실체를
가진 항목이 아니다. 이 방식을 쓰려면 그 자체가 근사이고, 위 2번(퀀타일 테이블)보다 나을 게
없다.

**이산적인 선택 문제가 생기면(예: 루트 테이블에서 항목 하나를 가중치로 고르는 것, `UEPLootTable`)
그때 이 메서드를 먼저 검토한다.** 지금 `UEPLootTable::RollLootTable`은 선형 스캔(가중치 누적
비교)이라 항목 수가 적을 때는 문제없지만, 항목이 크게 늘면 앨리어스 메서드로 O(1) 전환을
고려할 자리다.
